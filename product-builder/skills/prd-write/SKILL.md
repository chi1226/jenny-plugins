# 撰寫產品規格（PRD）

## 和 design-spec 的分工
[[design-spec]] 是「畫面層級」——一個畫面怎麼做。這個是「產品層級」——這個功能為什麼做、做到哪、怎麼算成功。順序通常是 PRD 先、design-spec 後。

## 輸入（使用者會填，空白先問）
- 功能 / 想法：［____］
- 目標使用者與他們的痛點：［____，有的話引用 [[problem-statement]] 或 [[job-story]]］
- 已知限制（時間、技術、資源）：［____］

## Task
產出一份 PRD：
1. **問題陳述**：誰、在什麼情境、遇到什麼問題、現在怎麼將就。
2. **Goals / Non-Goals**：這次要達成什麼（3 條內）；**明確列出不做什麼**——Non-Goals 是 PRD 最有價值的部分，防止範圍蔓延。
3. **User Stories**：作為［誰］，我想要［做什麼］，以便［得到什麼］。
4. **需求清單**：分 P0（沒有就不能上）/ P1（重要）/ P2（有更好），每條寫清楚可驗證的行為。
5. **成功指標**：上線後看什麼數據判斷成敗（可引用 [[product-metrics]]）。
6. **驗收條件**：QA 或自己驗收時逐條打勾的清單。
7. **分階段**（如果範圍大）：Phase 1 最小可上線 → Phase 2 之後補。
8. **Open Questions**：還沒定案、需要再研究或問人的事。

## 原則
- 寫「要解決什麼」不寫「介面長怎樣」——介面留給 design-spec。
- 每條需求都要可驗證：「載入要快」❌ →「列表 2 秒內顯示」✅。
- Non-Goals 至少列 2 條，逼自己劃界線。

## Output
完整 PRD（上述 8 節）＋一句話電梯簡報：「這功能幫［誰］解決［什麼］，成功的話［指標］會動。」
